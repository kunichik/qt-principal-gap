QBuffer tracks a counter up and down. But use of QBuffer outside of its own thread is probably a mistake, if not an outright bug, so I don't think that's a problem.

`QAbstractConnectionInterface` overrides the `disconnectNotify()` to be notified when a receiver disconnect and we no longer need to listen to the signal.
```
void QDBusAbstractInterface::disconnectNotify(const QMetaMethod &signal)
{
    // someone disconnecting from one of our signals
    Q_D(QDBusAbstractInterface);
    if (!d->isValid)
        return;

    // disconnection is just resource freeing, so it can be delayed;
    // let's do that later, after all the QObject mutexes have been unlocked.
    QCoreApplication::postEvent(this, new DisconnectRelayEvent(this, signal));
}
```
We could want to avoid double-posting of events, but we can't have zero events, which is the normal case when one disconnects from the interface's own thread.

QFutureWatcher base has code similar to QBuffer, but that one I don't know whether it could be used from outside its thread. But the worst case is that we have a delay in deciding whether to emit the `resultReadyAt()` calls. I don't think there's harm.
